# PODCAST LIVE RESEARCH

## 開発者向け入口

ブラウザ内の音声認識と Wikipedia / Wikidata 検索で、ポッドキャスト収録中の話題を調べる公開 Web アプリです。サーバーやデータベースはなく、静的ホスティングで動きます。作業ルールは [AGENTS.md](AGENTS.md) を読みます。

GitHub がコードと設定の共有元です。現在の共有ブランチは `main` です。

```bash
git clone --branch main https://github.com/m-miyazaki-collab/podcast-live-research.git
cd podcast-live-research
```

主な入口は `src/`（React画面、音声認識、話題抽出、Wikipedia/Wikidata連携）、`vite.config.ts`（静的配信設定）、`scripts/deploy.sh`（gh-pages への公開手順）、`package.json`（コマンド）です。文字起こしはブラウザのメモリ上で扱い、キャッシュと任意 AI 機能の設定は端末の localStorage に保存されます。アプリにサーバー、DB、収録音声の永続保存はありません。

初回確認:

```bash
npm install
npm run typecheck
npm run build
npm run preview
```

テスト用 script は `package.json` に定義されていません。`npm run deploy` は build 後に公開ブランチへ反映する操作なので、リリースの明示的な承認がある場合だけ実行します。この文書更新ではデプロイしていません。

最新状態は `git log -1 --oneline` と GitHub の [Pull requests](https://github.com/m-miyazaki-collab/podcast-live-research/pulls) / [Issues](https://github.com/m-miyazaki-collab/podcast-live-research/issues) で確認します。

ポッドキャスト収録中の会話を iPad のマイクでリアルタイム認識し、
いま話しているテーマに関する情報を横のモニターに出し続ける Web アプリ。

**「収録中、隣にリアルタイムで調査してくれるリサーチャーがいる」状態** を作るのが目的です。

- 音声認識: ブラウザ内蔵の Web Speech API（**無料 / APIキー不要**）
- 情報源: Wikipedia REST/Action API + Wikidata API（**無料 / APIキー不要 / CORS対応**）
- サーバー・DB: **なし**（100% クライアントサイド。静的ホスティングに置くだけ）
- ランニングコスト: **0円**

## 1. 何ができるか

1. `収録開始 / START` を押す → マイク許可 → 日本語のリアルタイム認識が始まる
2. 直近の会話（最大120秒）から「いま話している固有名詞」を推定
3. 同じ候補が 0.9〜1.8 秒続いたら Wikipedia / Wikidata を検索
4. **NOW** カードに 概要・重要な数値・年代・人物・場所・出典 を大きく表示
5. **RELATED** に会話を広げられる関連項目（タップで即座に開く）
6. **RECENT** に表示済みトピックの履歴（タップで戻れる）
7. **TRANSCRIPT** に確定/認識中を区別した文字起こし（`全文` で収録全体を確認）

会話例:

```
「この前名古屋に行ったんですよ」
「名古屋城も見てきて」
「そういえば名古屋城って誰が作ったんだっけ？」
        ↓
NOW: 名古屋城
     設立・創建 1532年 / 創設者 徳川家康 / 前身 那古野城 …
RELATED: 名古屋市・尾張国・二条城・江戸城・天守
```

### トピック検出の考え方（LLMなし）

日本語は「漢字・カタカナ・英数字の連続」が固有名詞になりやすく、助詞はひらがなです。
そこで **文字種の切れ目でトークン化 → ノイズ除去 → スコアリング** という素朴な方法を使います。

スコア = `新しさ(指数減衰) × 確度(確定文=1.0 / 認識中=0.75) × 語長 × 質問文に含まれるか(1.6倍)`

見るのは **直近30秒** だけ（10秒前の語は約1/3の重み）。話題が変わったら古い語がすぐ負けます。

さらに:

- 疑問詞で分割（`創業者誰` → `創業者`）
- 先頭にくっついた一般語を剥がす（`昨日トヨタ自動車` → `トヨタ自動車`）
- `AのB` 形の複合語を1語として拾う（`ノルウェイの森`、`関ヶ原の戦`）
- 上位語は下位語より優先（`名古屋` より `名古屋城`）
- 「創業者・意味・理由・歴史」など **属性を表す語** はトピックから除外
  （＝「知りたいこと」であって「話題」ではないため）
- 質問文（`〜だっけ` `〜ですか` `誰が` `いつ`）を検出して NOW カードに `Q:` として表示

### 「誰でも知っていること」を出さない仕組み

実収録で試すと、`自転車` `ヘッドフォン` `回転` のような一般名詞ばかり出てしまったため、
次の3段のフィルタを入れています。

1. **日常語ストップワード** — 自転車・電車・パソコン・映画などは最初から候補にしない
2. **記事の同一性チェック** — Wikipedia検索は何かしら返してしまうので、
   ヒットしたタイトルと語の長さがほぼ一致しない結果は捨てる
   （`ホームランバッター`→`本塁打`、`パッド`→`クックパッド` のような別記事の混入を防ぐ）
3. **中身の濃さチェック** — Wikidataに「生年・設立・所在地・作者」などの固有の事実が
   **2件以上** ある項目だけを自動表示する。一般名詞はここでほぼ落ちる
   （`自転車`=1件 / `ヘッドフォン`=1件 / `回転`=0件 → 除外、`名古屋城`=10件 / `大谷翔平`=10件 → 採用）

3つ全部を通らなかった場合は **前のカードを消さずに何も出しません**。
1つ目の候補がダメなら2番目・3番目の候補を自動で試すので、雑音の多い認識結果でも会話に追従します。
除外した語は端末に記録し、二度と検索しません。

**情報源が取れない内容は推測で埋めません。**

### 質問への「答え」を出す

質問（`〜だっけ` `誰が` `いつ` `どこ`）を検出したら、疑問詞に対応する項目を
カードの最上段に大きく出します。文章は生成せず、Wikidataの値をそのまま出すだけです。

```
Q: 名古屋城って誰が作ったんだっけ
   → 創設者  徳川家康
Q: 大谷翔平って何歳だっけ
   → 生年    1994年7月5日
```

### 画像

NOWカードには Wikipedia の代表画像を大きく載せます（RECENT履歴にもサムネイル）。
文字を読む前に「何の話か」が見えるようにするためです。

画像は Action API の `piprop=thumbnail&pithumbsize=600` で取得します。
RESTのsummaryが返すサムネイルは約320pxで、URLの幅を書き換えても
Wikimedia側が生成済みの幅しか配信しないため 400 になります（要注意）。
なお概要・画像・Wikidata項目IDは **この1リクエストでまとめて** 取れるので、通信量は増えていません。

### 情報カードの項目は固定していない

Wikidata のプロパティのうち、そのエンティティが実際に持っているものだけを優先度順に最大8件出します。

- 人物 → 生年 / 没年 / 職業 / 役職 / 出生地 …
- 企業 → 設立 / 創設者 / 本社 / 業種 / 従業員数 …
- 建造物 → 設立・創建 / 創設者 / 所在地 / 文化財指定 / 前身 …
- 出来事 → 発生時期 / 場所 / 参加者 …

### RELATED の作り方

2系統を混ぜています。

1. 記事の導入部（section 0）のリンク＝その項目の説明に不可欠な語（名古屋城 → 尾張国 / 那古野城）
2. `morelike:` 検索＝似ている記事＝話を横に広げられる語（名古屋城 → 二条城 / 江戸城 / 天守）

## 5. リクエストを増やさないための仕組み

無料運用が前提なので、以下を実装しています。

| 仕組み | 内容 |
| --- | --- |
| debounce | 同じ候補が 1.8 秒（確定文なら 0.9 秒）続いたときだけ検索 |
| 同一トピック抑止 | いま表示中／検索中のトピックは再検索しない |
| メモリキャッシュ | 同一セッション内は即時ヒット |
| localStorage キャッシュ | 7日間保持（最大120件、古いものから破棄）。**リロードしても残る** |
| ネガティブキャッシュ | 「記事が無い語」を1日覚えて無駄打ちを防ぐ |
| レートリミット | 自動検索はトークンバケット（バースト8 / 12回per分）。超過時はヘッダーに `レート制限中` と表示し、キャッシュのみで動作 |
| 手動タップは即時 | RELATED / RECENT / CANDIDATES のタップは制限を迂回して即取得 |

1トピックあたりのリクエストは 4〜5 本（summary / lead links / morelike / wikidata×1〜2）です。

## 6. 音声認識の安定性（iPad Safari 対策）

Web Speech API は連続認識が勝手に止まります。そのため:

- `onend` → ユーザーが STOP を押していなければ自動再開
- `onerror` → `no-speech` / `aborted` / `network` は復帰対象、`not-allowed` / `audio-capture` は明確なエラー表示で停止
- `visibilitychange` / `focus` → バックグラウンド復帰時に再開
- 再起動は **指数バックオフ（250ms → 最大4秒）**、20秒間に12回を超えたら停止して
  「STARTを押し直してください」と表示（**無限再起動ループ防止**）
- 収録中は Wake Lock で画面を消さない（対応端末のみ）

Web Speech API 非対応のブラウザでは、その旨をバナーで明示します。

### 既知の制約

- iPadOS Safari の音声認識は端末やOSバージョンによって挙動が変わります。長時間の連続収録では
  数分おきに再接続（ヘッダーが `RECONNECTING` になる）が起きることがあります。
- 形態素解析を使わないため、ひらがなだけの固有名詞（例:「ちいかわ」）は検出できません。
- **このアプリは録音しません。** 文字起こしはメモリ上のみで、リロードすると消えます
  （キャッシュされるのは情報カードと RECENT だけです）。

## 7. AI機能（既定では無効・任意）

初期状態では **AI API を一切使いません**。`設定` からキーを登録した場合だけ
NOW カードの `AIで調べる` が有効になり、**押したときだけ** リクエストが飛びます。

- APIキーはコードに埋め込まず、端末の localStorage にのみ保存
- Anthropic (Claude) / OpenAI互換エンドポイントの2系統に対応（`src/lib/ai.ts`）
- 送信内容は「現在のトピック + 直近60秒の文字起こし + 質問」
- プロンプトには「確実でない点は未確認と書く」「出典を添える」を明示

> 本番運用では、キーをブラウザに置かずに済むよう **Cloudflare Workers 等の無料枠でプロキシ** を挟み、
> `プロバイダ = OpenAI互換` + `エンドポイント = 自前URL` を指定する構成を推奨します。

### 後から足しやすくしてある機能

`ai.ts` の `AiTask` を増やすだけで乗る想定です。

1. リアルタイムファクトチェック（`task: 'factcheck'`）
2. 「今の発言、正しい？」ボタン
3. AIリサーチ / 会話の広げ方提案（`task: 'expand'`）
4. Google検索等との連携（`lib/` に provider を追加）
5. Speaker識別（`TranscriptChunk` に `speaker` を追加）
6. 収録後の全文Transcript（すでに全文保持済み。エクスポートを足すだけ）
7. 自動チャプター生成 / 8. Show Notes生成 / 9. 出典一覧 / 10. 要確認事項一覧
11. PWA化（manifest 同梱済み。Service Worker を足すだけ）
12. ホーム画面起動（`apple-mobile-web-app-capable` 設定済み）

## 8. 動作確認済みの内容

`npm run build`（tsc + vite）に加えて、ブラウザ上で以下を実測しています。

- トピック抽出: 「この前名古屋に行った → 名古屋城も見てきて → 名古屋城って誰が作ったんだっけ？」→ `名古屋城`
- 雑談のみ（固有名詞なし）→ 検索を発生させない
- 収録シミュレーションから NOW / RELATED / RECENT / TRANSCRIPT の表示まで一連の動作
- RELATED タップ → 新しい NOW カード、RECENT タップ → 過去のカードへ復帰（追加リクエスト 0）
- リロード後もキャッシュと RECENT が残る
- `onend` からの自動再開、`not-allowed` エラー時の停止＋エラー表示、再起動ループが暴走しないこと
